## 1. Что построено

Пайплайн `quakes_elt` (Airflow 2.11.2): `load_raw → dbt_build_candidate → dbt_test → publish`. Из среза USGS (212 событий M≥2.5, 2025-03-03…05 UTC) строится факт `dds.fact_earthquake` (210 землетрясений; 2 `mining explosion` исключены бизнес-правилом) и витрина «день × класс магнитуды × сеть» (27 строк). Потребитель читает только `mart.daily_quakes`; кандидат строится и проверяется в `mart_candidate`.

Количество строк по слоям (`evidence/layers.txt`): raw 212 → ODS 212 версий и 212 актуальных → факт 210 → витрина-кандидат 27 → опубликовано 27. Полнота относительно источника: `count`-запрос USGS за то же окно возвращает 212 — совпадает с raw.

## 4. Успешный запуск, повтор и сравнение

Два запуска подряд на одинаковом исправном входе (`first_success`, `second_success`) сравнены не по `count(*)`, а по содержимому: `EXCEPT` в обе стороны и md5 всех строк (`evidence/idempotent_repeat.txt`):

- витрина: 27 vs 27 строк, `only_in_run1 = 0`, `only_in_run2 = 0`, md5 `6d50889e…` = `6d50889e…`;
- факт: 210 vs 210, `only_in_* = 0`, md5 `29771c41…` = `29771c41…`;
- контрольные суммы в `mart.publication_log` для двух публикаций совпадают.

Идемпотентность обеспечивают: raw — детерминированная функция выбранного входа (`truncate` + `copy` в одной транзакции), модели не зависят от времени запуска, актуальное состояние выбирается по явному порядку, публикация заменяет окно целиком. Возврат к baseline после каждого случая тоже сверен: `IDENTICAL` против первого снимка.

**Параллельные запуски.** У DAG `max_active_runs=1`: при одновременном запуске `parallel_b` стоял в `queued`, пока шёл `parallel_a`, и стартовал только после его завершения (`evidence/concurrency.txt`). Дополнительно `publish.py` берёт `pg_advisory_xact_lock(7331)`, так что даже запуск публикации вне Airflow не пересечётся с другой публикацией. Для учебного решения этого достаточно (сериализация).

## 5. Ошибка качества: блокировка публикации и восстановление

Вход `corrupt`: одно событие `corrupt_0001` с магнитудой 99 (остальные поля скопированы с реального события).

- **Результат запуска `case_corrupt`:** `load_raw` и `dbt_build_candidate` — success (dbt построил кандидата), `dbt_test` — **failed**, `publish` — **upstream_failed** (`screenshots/02_quality_failure_graph.png`).
- **Диагностика в логе** (`screenshots/03_quality_failure_log.png`, `evidence/corrupt_blocked.txt`): упали `magnitude_and_depth_in_range`, `not_null_fact_earthquake_mag_class_key`, `not_null_mart_daily_quakes_class_key` — `PASS=29 ERROR=3`.
- **Конкретная строка:** `select * from dbt_test_audit.magnitude_and_depth_in_range` → `event_id = corrupt_0001`, `magnitude = 99`, `depth_km = 65.29`. По `raw.usgs_events where _slice_id = 'corrupt'` видно, что строка пришла из синтетической дельты `corrupt` (`_is_synthetic = t`).
- **Причина:** магнитуда 99 вне допустимого диапазона −2…10, поэтому событие не попадает ни в один класс шкалы (`mag_class_key` пуст) — сработали проверка диапазона и `not_null` в факте и в витрине.
- **Кандидат и публикация разделены:** dbt сам не откатывает таблицы кандидата (они содержат ошибочную строку), но потребитель видит прежнюю публикацию: md5 `mart.daily_quakes` равен baseline, число записей в `publication_log` не выросло (12), последняя — `restore_after_overlap` (`screenshots/05_publication_log_after_error.png`, `06_mart_totals_after_error.png`: 74 / 76 / 60).
- **Восстановление:** запуск без случая (`restore_final`) — все 4 задачи success, витрина идентична baseline.

| Проверка | Где |
|---|---|
| Заполненность и уникальность ключей: `event_key` (stg и fact), `network_key`, `class_key`, `date_key`, ключевые поля витрины | `models/*/*.yml` |

| Сверка слоёв: число землетрясений в ODS = число строк факта; события витрины за день = события факта | `tests/fact_matches_stg_count.sql`, `tests/mart_reconciles_with_fact.sql` |
| Зерно витрины уникально | `tests/mart_grain_unique.sql` |
| История: интервалы версий сети не пересекаются; ровно одна версия сети на событие | `tests/network_history_no_overlap.sql`, `tests/one_network_version_per_event.sql` |

Singular-тесты возвращают нарушившие строки, `store_failures` сохраняет их в `dbt_test_audit.*`. Всего 32 теста, на baseline `PASS=32`.

## 7. Ограничения решения

- Уникальность ключа не доказывает полноту выгрузки: если бы USGS отдал не все события окна, тесты бы прошли. Единственный контроль полноты — ручное сравнение с ответом `count` источника (212 = 212), встроенной проверки нет.
- Ломающиеся касты типов (например, нечитаемое `time`) роняют `dbt run`, а не тест: сообщение об ошибке менее конкретно, чем у тестов качества.
- Raw пересоздаётся целиком на каждый запуск (truncate + copy), это не накопительный слой с историей загрузок
- Публикация заменяет окно дат в целом; если событие со временем выходит из окна (например, USGS сдвинул время), старая строка в `mart.daily_quakes` останется до пересчёта её окна.
