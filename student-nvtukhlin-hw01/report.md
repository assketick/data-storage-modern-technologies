## 1. Паспорт источника

- **Название**: Wikimedia Pageviews dumps (почасовые просмотры страниц всех проектов Wikimedia).
- **Официальная ссылка**: https://dumps.wikimedia.org/other/pageviews/ (описание формата: https://dumps.wikimedia.org/other/pageviews/readme.html).
- **Дата получения**: 2026-09-16 (использованы архивные файлы за 2015-05-01 — сами дампы историчны, но раздаются официально и стабильно по прямой ссылке).
- **Лицензия/условия**: CC0 (Public Domain), см. страницу дампов; терминологически данные — публичная статистика просмотров, персональных данных не содержат.
- **Исходный формат и размер**: два файла `.gz` по одному часу каждый, `pageviews-20150501-010000.gz` (42.3 МиБ) и `pageviews-20150501-020000.gz` (41.8 МиБ). Внутри — текст без заголовка, поля через пробел: `domain_code page_title count_views total_response_size`. Час и дата не хранятся в строках — только в имени файла.
- **Единица наблюдения**: число просмотров одной страницы `en.wikipedia.org` за один конкретный час.
- **Границы выборки**: только `domain_code == 'en'` (обычная английская Wikipedia, без мобильной версии и других языковых разделов), два часа одного дня — `2015-05-01 01:00:00 UTC` и `2015-05-01 02:00:00 UTC`. Выбор двух часов — намеренный: это естественные непересекающиеся порции для двух записей в Iceberg (шаг 5).
- **Исследовательский вопрос**: как распределяются просмотры между основным энциклопедическим контентом (обычные статьи) и остальными пространствами имён MediaWiki (обсуждения, файлы, категории, служебные страницы), и какие из этих групп получают больше всего просмотров?
- **Известные ограничения**:
  - `total_response_size` всегда `0` — поле устарело и не заполняется дампами этой эпохи, это не ошибка данных.
  - Данные историчны (2015 год), а не текущие — для целей ДЗ (демонстрация pipeline) это не важно, но делать выводы о поведении читателей Wikipedia "сегодня" нельзя.
  - Взяты только 2 часа одного дня — недостаточно для суточных/недельных паттернов, только для сравнения двух точек во времени.
  - Namespace-классификация построена по префиксу заголовка и списку известных namespace en.wikipedia; несколько тысяч заголовков с двоеточием внутри самого имени статьи (например, `ISO_3166-2`) корректно не считаются namespace и попадают в `(article)`.

## 2. Raw без скрытых изменений

Команда получения данных:
```bash
curl -O https://dumps.wikimedia.org/other/pageviews/2015/2015-05/pageviews-20150501-010000.gz
curl -O https://dumps.wikimedia.org/other/pageviews/2015/2015-05/pageviews-20150501-020000.gz
```
Загрузка в raw бакет без изменений — `01_upload_raw.py`, ключи:
```
s3://raw/nvtukhlin/wikipageviews/ingestion_date=2026-09-16/pageviews-20150501-010000.gz  (42.3 МиБ)
s3://raw/nvtukhlin/wikipageviews/ingestion_date=2026-09-16/pageviews-20150501-020000.gz  (41.8 МиБ)
```
Полный листинг — `evidence/object-listing.txt`. Raw не редактировался вручную.

Так как источник не CSV, отдельным воспроизводимым шагом (`02_prepare_csv.py`) подготовлен табличный
CSV: распаковка `.gz`, фильтр `domain_code == 'en'`, добавление `event_date`/`event_hour` из имени
файла. Результат — `s3://datalake/nvtukhlin/wikipageviews/staging_csv/wikipageviews.csv` (105.38 МиБ,
2,600,099 строк с заголовком) — это staging-слой, а не raw.

## 3. Явная схема и DQ

Схема задана явно в `pipeline.py` (`CSV_SCHEMA`, без `inferSchema=True`). Обязательные проверки
(функция `validate`):

| Проверка | Результат |
|---|---|
| Число строк > 0 | 2,600,099 |
| Ключевые столбцы существуют | все 6 столбцов CSV присутствуют (иначе `FAILFAST` упал бы при чтении) |
| Временной столбец парсится | `event_date`/`event_hour` — 0 некорректных |
| Числовая мера без невозможных значений | `count_views < 0` — 0 строк |
| Доля NULL в ключевом поле (`page_title`) | 0.000000 |
| raw = accepted + rejected | 2,600,099 = 2,600,099 + 0 |

Отклонённых строк нет — это ожидаемо и объяснимо: источник уже агрегирован на стороне MediaWiki
(по одной строке на `page_title` в файле), грязных строк или дублей в дампе не бывает. Проверка
воспроизводима (пересчитывается каждый прогон), искусственные ошибки не добавлялись, как и
разрешено условием ДЗ при нулевом результате.

Один встретившийся нетривиальный случай при чтении: реальный заголовок статьи
`"Boys_are_stupid,_throw_rocks_at_them!"_controversy` содержит кавычки и запятую и после
CSV-квотирования (`02_prepare_csv.py`) ломал стандартный Spark CSV-reader (по умолчанию
`escape='\'`, а не `'"'`, поэтому RFC4180-двоение кавычек `""` не распознавалось). Исправлено
опцией `.option("escape", '"')` в `pipeline.py` — без неё падал `FAILFAST` на этой строке.

## 4. Parquet и измерения

Запись: `s3://datalake/nvtukhlin/wikipageviews/parquet/`, партиционирование — **`event_hour`**
(2 значения: 1 и 2). Выбор объясняется просто: это ровно та же граница, что разделяет две
непересекающиеся порции для Iceberg (шаг 5), и партиций всего 2 — не по уникальному идентификатору
(`page_title` для партиционирования не используется).

Измерения (полный вывод — `evidence/spark-result.txt`):

| Метрика | Подготовленный CSV | Parquet | Как измеряли |
|---|---|---|---|
| Размер, МиБ | 105.38 | 32.87 | `getContentSummary` по пути в MinIO после записи |
| Число строк | 2,600,099 | 2,600,099 | `count()` после чтения |
| Время одного аналитического запроса, с (1-й / 2 повтора) | 1.329 / 1.079 / 0.629 | 0.416 / 0.276 / 0.194 | `time.perf_counter()` вокруг `spark.sql(QUERY).collect()`, схема задана заранее, кэш не сбрасывался между форматами (не холодный старт) |
| Поля, используемые запросом | `namespace`, `count_views` (group by + sum) | те же | `SELECT namespace, count(*) AS pages, sum(count_views) AS total_views FROM ... GROUP BY namespace` |

Отношение размеров CSV/Parquet — 3.21×. На этом запросе и в этом прогоне Parquet стабильно
быстрее CSV (в ~3–5 раз) — в отличие от учебного синтетического примера на 200 тыс. строк, где
разница между форматами была в пределах шума. На 2.6 млн строк выигрыш от колоночного формата и
предиктивной обработки чтения (меньше данных на диске, эффективнее I/O) стал заметен сильнее.
Это не универсальный закон: результат одного прогона на одном ноутбуке, без явного прогрева JVM
и при разделяемых с другими сервисами ресурсами Docker.

## 5. Iceberg

Таблица: `lakehouse.nvtukhlin.wikipageviews`. Две записи из непересекающихся порций:

1. **CTAS** первой порции — `event_hour = 1` → 1,294,434 строк.
2. **INSERT** второй порции — `event_hour = 2` → итог 2,600,099 строк (1,294,434 + 1,305,665 =
   2,600,099, совпадает с полным принятым набором).

Изменение схемы отдельно не выполнялось — оба шага реально писали новые файлы данных.

```
snapshot_id           committed_at                operation  total_records
8075560864216313162   2026-09-16 16:19:43.199     overwrite  1294434
4163048399897555244   2026-09-16 16:19:44.944     append     2600099
```
(В `evidence/trino-result.txt` видно ещё одну пару snapshot'ов от повторного прогона — это ожидаемо,
`CREATE OR REPLACE` не стирает историю снимков предыдущего запуска.)

Связь каталога, метаданных и файлов: JDBC-каталог (PostgreSQL) хранит только указатель на текущий
`metadata.json` таблицы; сам `metadata.json` в MinIO (`s3://datalake/warehouse/nvtukhlin/wikipageviews/metadata/`)
перечисляет snapshot'ы и manifest-файлы (`*.avro`), а manifest'ы указывают на конкретные
Parquet-файлы с данными (`s3://.../data/event_hour=1/*.parquet` и `event_hour=2/*.parquet`).
`overwrite` создал новый metadata.json и manifest, ссылающийся на файлы первой порции; `append`
добавил новый metadata.json, который ссылается на manifest первой порции **и** новый manifest
второй — старые файлы не переписываются, снимки — это просто разные версии списка ссылок на
Parquet-файлы.

## 7. Федеративный SQL

Справочник `memory.default.namespace_groups` (в памяти Trino, непостоянный, восстанавливается
`queries.sql`) сопоставляет 4 из ~20 встречающихся namespace человекочитаемым группам:
`(article)` → «Основной контент», `Category` → «Категоризация», `File` → «Медиафайлы»,
`Talk` → «Обсуждения». Остальные (Special, User, Wikipedia, Template, Portal и т.д.) намеренно не
покрыты, чтобы показать обработку несопоставленных строк.

`LEFT JOIN lakehouse.nvtukhlin.wikipageviews` с этим справочником, `coalesce(..., 'Не сопоставлен')`:
```
Основной контент   2,322,536 стр.  11,451,033 просм.
Не сопоставлен        103,759 стр.     679,052 просм.
Медиафайлы             92,542 стр.     213,990 просм.
Категоризация           63,170 стр.    129,345 просм.
Обсуждения              18,092 стр.     26,032 просм.
```
Ключи справочника уникальны (проверочный запрос вернул 0 строк). Строки не потеряны и не
размножены: `before_join = after_join = 2,600,099`, из них `unmatched = 103,759`.

- **Каталоги**: `lakehouse` (Iceberg/JDBC-каталог, физическое хранилище — MinIO) и `memory`
  (временный in-process каталог самого Trino).
- **Физически данные**: факт-таблица — Parquet-файлы в MinIO; справочник — только в оперативной
  памяти процесса Trino, исчезает при рестарте контейнера.
- **Что делает Trino во время запроса**: читает список файлов через Iceberg-метаданные (JDBC
  catalog → metadata.json → manifest → Parquet), сканирует нужные Parquet-файлы, одновременно строит
  in-memory таблицу справочника и выполняет `LEFT JOIN` и агрегацию в собственном движке — без
  переноса данных в третье хранилище.
- **Почему это федерация**: один SQL-запрос объединяет данные из двух независимых источников с
  разной природой хранения (постоянный колоночный Iceberg-слой в S3 и временная таблица в памяти)
  так, будто это одна база — само распределение и чтение из разных мест скрыто внутри Trino.

## 8. Архитектурный вывод

S3-слой (MinIO) дал дешёвое и универсальное хранилище для сырых файлов и файлов таблицы, не
привязанное к конкретному движку. Parquet добавил колоночное сжатие (×3.21 в этом прогоне) и
позволил читать только нужные столбцы, из-за чего аналитический запрос на 2.6 млн строк выполнялся
в разы быстрее, чем на CSV. Iceberg поверх Parquet добавил транзакционные снимки (snapshots),
явную схему на уровне таблицы и возможность добавлять данные порциями без риска дублей или
частичной записи — то, чего у голых Parquet-файлов нет. Spark нужен для тяжёлой пакетной обработки
и записи (DQ-проверки, запись в Parquet/Iceberg), а Trino — для интерактивного SQL и федеративных
запросов поверх уже готовых таблиц; развести эти роли на два движка позволяет не гонять
интерактивные запросы через тяжёлый Spark-джоб и не писать батчевые ETL через SQL-движок. Самое
слабое место текущего локального решения — единственный узел без реплик и без выгрузки/архивации
snapshot'ов: PostgreSQL как единая точка отказа для каталога, MinIO без резервирования данных, а
`memory` catalog у Trino теряет содержимое при любом рестарте контейнера.
